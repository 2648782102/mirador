# How Mirador is built

The server's modules and how it reads Engram and starts agent terminals. The short version, with a diagram, is in the [README](../README.md#how-it-works).

## How it works

```
Chromium app window ──HTTP/WebSocket──▶ src/server.ts (127.0.0.1 only)
                                          ├─ http/routes/*.ts      one module per API feature (docs/extending.md)
                                          ├─ workspaces/store.ts   workspaces: validation, saving, root guard per workspace
                                          ├─ folders/tree.ts       folder listing, root guard
                                          ├─ folders/git-status.ts read-only git state of a folder (plain mode)
                                          ├─ folders/git-diff.ts   read-only diff of a folder against HEAD (Changes view)
                                          ├─ terminals/registry.ts node-pty sessions + scrollback
                                          ├─ terminals/open-agents.ts open agents, reopened after a restart
                                          ├─ memory/engram.ts      Engram HTTP client
                                          └─ memory/daily-summary.ts pure summary building
```

- The web UI is bundled at boot: `src/http/bundle.ts` runs esbuild in memory and `/` loads one JS and one CSS bundle (6 requests instead of ~100), rebuilt on the next request after a change in `public/`; if bundling fails it logs once and serves the unbundled files, which stay at their URLs.
- Each build is minified and kept in memory three ways: as is, gzip (level 6) and brotli (quality 9 at build time, about 45 ms; quality 11 replaces it in the background about 1.5 s later). The server picks one from `Accept-Encoding` (`vary: accept-encoding`; no header means uncompressed). The bundles are named by their content hash, `/bundle/app.<hash>.js` and `.css`, and cached for a year (`immutable`); `/` is `no-cache`, so the next load after an edit in `public/` names the new hash, and an old hash answers 404. `/bundle/app.js` and `/bundle/app.css` still answer the current build, `no-cache`. The unbundled fallback is served from disk as before, uncompressed.
- The page reads its start-up state with one `GET /api/bootstrap`: `{ config, workspaces }`, each the body of `GET /api/config` and `GET /api/workspaces`, run in-process through their own handlers (`src/http/routes/bootstrap.ts`). Both endpoints stay as they are.
- Plain mode's "Where it left off" reads `GET /api/folder/git?ws=&rel=` → `{ cwd, git, notes, leftOff? }` (`src/http/routes/git-status.ts`), never Engram. `leftOff`, only when the folder has one, is its local record of Claude Code's hooks (`src/memory/left-off.ts`, see [Where it left off](attention.md#where-it-left-off)) as `{ source: 'claude-code', from, at, text, lastUserMessage }`, each text clipped to 12 lines. `src/folders/git-status.ts` (`folderGitStatus(root, rel)`) runs only `rev-parse`, `symbolic-ref`, `log` and `status --porcelain=v1 -z`, all with `--no-optional-locks` and `GIT_OPTIONAL_LOCKS=0` (the index is never refreshed or written), `-c core.fsmonitor=false` (no fsmonitor hook runs), `-c log.showSignature=false`, set once by the shared runner (`runGit`) so no call can miss them, git started from an argument array without a shell (`execFile`, `shell: false`) and every path passed only after `--`, so a file named `--output=x`, `-n.txt`, `a b.txt` or with a line break is a name, never an option, Mirador's own `GIT_*` variables removed, `LC_ALL=C` and a 5 s timeout per command. The work tree must lie inside the workspace root: `GIT_CEILING_DIRECTORIES` is the root's parent, so a repository above the root is never found (`not_repo`), and a repository whose work tree lies outside the root (`core.worktree`) answers `outside_root`. The repository's own data may lie elsewhere: a `.git` file whose `gitdir:` points outside the root, as `git worktree` makes, is read, read-only like everything else. No repository, no git on `PATH` or git failing answer `{ available: false, reason }` (`not_repo`, `outside_root`, `git_missing`, `git_failed`), never an error. `src/folders/notes.ts` reads `NOTES.md` (exact name, a regular file, a symlink only when it stays inside the root, no NUL bytes) up to 16 KB, cut on a whole character; the UI shows it as text, never as HTML. Both resolve the folder with `resolveInsideRoot` (`src/folders/tree.ts`), as every folder route does through `ctx.resolveFolder`.
- The **Changes** panel view, in both modes, reads `GET /api/folder/diff?ws=&rel=` → `{ cwd, diff }` (`src/http/routes/git-diff.ts`). `src/folders/git-diff.ts` (`folderGitDiff(root, rel)`) goes through the same `openRepo` confinement and `runGit` runner as the git state above, and runs only `rev-parse --verify HEAD^{commit}`, `config --get-regexp '^filter\.'`, `diff --numstat -z` and `diff --patch` against `HEAD` (staged and unstaged together, limited to the folder with pathspec `.`, paths from the repo root) and `ls-files --others --exclude-standard --directory` (untracked names only, never their content). Because a diff reads file contents, it also turns off the index refresh `git diff` does on its own (`-c diff.autoRefreshIndex=false`: a file whose stat changed but whose content did not would otherwise make it rewrite `.git/index` and run `post-index-change`, which `--no-optional-locks` does not stop) and every program the repository's config could name: `--no-ext-diff` and `-c diff.external=`, `--no-textconv`, `--no-pager`, every `filter.<driver>` found in the config emptied through `GIT_CONFIG_COUNT` (no clean, smudge or process filter), `GIT_NO_LAZY_FETCH=1` (a partial clone never fetches) and `--ignore-submodules=dirty` (no git run inside submodules). Binary files come as `binary: true` without content. Output is capped: each file's diff is cut at 64 KB on a line end and at most 512 KB of diff is kept in all (`truncated`, shown as "diff truncated" / «diff truncado» on the file). git's patch output is read 512 KB at a time: when a huge file fills a read, the files after it are read again with `diff --numstat -z --patch HEAD -- ':(top,literal)<path>'…` (both sides of a rename, paired by path from the stat part), at most 10 reads per answer, so one huge file never leaves the others without a diff. At most 200 files and 100 untracked names are listed while `totals` and `untracked.count` count them all, and `complete: false` says something was left out. A repository without commits answers `no_commits`; the other reasons are those of the git state. The view colours lines by kind (`public/features/changes-model.js`: file header, hunk header, added, removed, context) with CSS classes on spans whose only child is the line's text, never HTML.
- **Clean filters and Git LFS.** A `.gitattributes` line such as `*.bin filter=lfs` only names a filter driver; a program runs only when `filter.<driver>.clean` or `filter.<driver>.process` is set in git's config (the repository's `.git/config`, `~/.gitconfig`, `~/.config/git/config` or the system config). A cloned repository cannot set that by itself, because `git clone` copies no config: a clean filter is always one the user, or a tool the user ran (`git lfs install`), configured. The git state does not disable filters: when a tracked file's stat changed since the index recorded it (a stale index), `git status` runs that file's configured clean filter to compare its content with the index, as the user's own `git status` would, with the user's permissions and inside the 5 s timeout. Mirador lets it, because without the filter every Git LFS file whose stat changed would look modified (the work tree holds the content, the index and `HEAD` hold the pointer). The index is still not written, so the filter runs again on each query until a git command of the user's refreshes the index. The Changes panel does empty every filter (above), so git compares the raw work-tree file with what `HEAD` stores. For a Git LFS file that means: unchanged and untouched, it is listed in neither view (git trusts the index stat and reads nothing); changed, the git state lists it as ` M` and the Changes panel shows the `HEAD` pointer (`version https://git-lfs.github.com/spec/v1`, `oid sha256:…`, `size …`) removed and the raw content added, or `binary: true` when the content is binary, not the pointer-to-pointer diff a plain `git diff` shows; touched without a change (stale stat only), the git state does not list it but the Changes panel does, with the same pointer-to-content diff. Checked on 2026-11-12 with git 2.56.1, a `filter.<x>.clean` that leaves a marker, a local clone of that repository, and an LFS-like driver (`filter.lfs.clean` storing the content and printing a pointer, `filter.lfs.smudge` restoring it), all without network. `git lfs` was not installed, so the real `git-lfs` program was not run; its `filter.lfs.process` is emptied in the Changes panel like any other filter variable.
- Folder → Engram project uses Engram's own `GET /project/current?cwd=`, so it matches what agents save.
- The **no memory** tag comes from one `GET /projects` (cached 30 s; it gives up after 1 s and a failure is remembered for 5 s, so a slow or odd Engram never holds the tree up), not one request per folder: a folder has memory when a project with observations lists a directory at or below it, or is named like the folder. It is an approximation: a project used only from a parent folder does not count, and two folders with the same name share the answer. Ambiguous container folders fall back to the `directories` that `GET /projects` reports.
- Days are local calendar days (`timeZone`); Engram stores UTC.
- Engram's recent endpoints have no date filter or paging, so a summary reads the newest 5000 observations and sessions. `GET /api/summary` and `GET /api/activity` answer `truncated: true` when that window may not reach back to the start of the requested day (it held 5000 entries and the oldest is from that day or later). The all-projects window behind the overview, the activity view and container summaries is read once and shared for 3 s.
- An agent terminal runs `bash --rcfile <runtime>/agent.bashrc -i`: it loads `~/.bashrc`, then runs `agentCommand`. Leaving the agent drops you to that bash in the same folder. That bash marks each prompt it draws with OSC 133 A (appended to your `PROMPT_COMMAND`, keeping `$?`; a readonly `PROMPT_COMMAND` is left alone). A prompt means nothing runs in the foreground, so when the agent exits or dies Mirador drops the `working` and `blocked` statuses it reported with OSC 7501, and its answer card leaves the inbox. The wait its hooks reported for that same terminal (`blocked`, `prompt`) ends too; `done`, `error` and a finished turn stay (source `src/terminals/agent-rc.ts`, `AttentionStore.programPrompt`). Variables leaked by a parent gentle-shell or Claude Code session (`PI_CODING_AGENT_DIR`, `ENGRAM_BIN`, `CLAUDECODE`, `CLAUDE_CODE_*`, `MIRADOR_*`), plus a parent tmux session's `TMUX` and `TMUX_PANE`, are removed (`cleanEnv` in `src/terminals/registry.ts`).
